# 카프카 (Apache Kafka)

> 처음 쓰는 사람 기준으로, **용어 → 개념 → 쓰는 법** 순서로 정리한다.

---

## 한 줄 요약

**카프카는 메시지를 쌓아두고, 여러 시스템이 나눠 가져가게 해주는 메시지 중계소**다.  
채팅처럼 "지금 당장 주고받기"보다, **대량 이벤트를 안정적으로 흘려보내는** 쪽에 강하다.

---

## 왜 쓰나?

웹 서비스에서 이런 일이 자주 생긴다.

1. 주문이 들어온다
2. 재고를 깎아야 한다
3. 결제 로그를 남겨야 한다
4. 알림도 보내야 한다

이걸 전부 한 API 안에서 순서대로 하면?
- 하나가 느려지면 전체가 느려진다
- 하나가 죽으면 주문 자체가 실패한다

그래서 **"일단 이벤트만 카프카에 던져두고, 각자 알아서 처리"** 하는 방식이 나온다.

```
[주문 API] --주문완료 이벤트--> [카프카] --구독--> [재고 서비스]
                              |          --구독--> [알림 서비스]
                              +----------구독--> [로그 서비스]
```

---

## 핵심 용어

| 용어 | 쉬운 말 |
|------|---------|
| **Producer (프로듀서)** | 메시지를 **보내는** 쪽 |
| **Consumer (컨슈머)** | 메시지를 **받는** 쪽 |
| **Broker (브로커)** | 카프카 서버 한 대. 메시지를 받아서 저장한다 |
| **Cluster (클러스터)** | 브로커 여러 대를 묶은 것 |
| **Topic (토픽)** | 메시지 분류함. 예: `order-created`, `user-signup` |
| **Partition (파티션)** | 토픽을 나눈 칸. 병렬 처리용 |
| **Offset (오프셋)** | 파티션 안 메시지 번호. "여기까지 읽었다" 표시 |
| **Consumer Group** | 컨슈머를 묶은 팀. 같은 그룹은 일을 나눠 받는다 |
| **Message / Record** | 실제 데이터 한 건 (보통 JSON) |

---

## 개념을 그림으로

### 1) 토픽 = 주제별 편지함

```
토픽: order-created
┌─────────────────────────────┐
│ msg1 | msg2 | msg3 | msg4 … │
└─────────────────────────────┘
```

- 프로듀서: `order-created`에 넣는다
- 컨슈머: `order-created`를 구독해서 꺼낸다

### 2) 파티션 = 같은 편지함을 칸으로 나눔

한 토픽을 파티션 여러 개로 나누면 **동시에 여러 컨슈머가 읽을 수 있다.**

```
토픽: order-created
  파티션 0: [A] [B] [C]
  파티션 1: [D] [E]
  파티션 2: [F] [G] [H]
```

같은 Consumer Group 안에서는 **파티션 1개 = 컨슈머 1명**이 담당한다.  
(컨슈머가 파티션보다 많으면 남는 컨슈머는 논다)

### 3) 오프셋 = 북마크

```
파티션 0: [0] [1] [2] [3] [4]
                 ↑
            여기까지 읽음 (offset = 2)
```

카프카는 "전달했다"고 바로 지우지 않는다.  
**일정 기간 보관**하고, 컨슈머가 오프셋으로 "어디부터 읽을지" 정한다.  
그래서 장애 났을 때 **다시 읽기(replay)** 가 가능하다.

### 4) Consumer Group = 역할 분담

| 상황 | 동작 |
|------|------|
| 그룹 A에 컨슈머 1명 | 모든 파티션을 혼자 읽음 |
| 그룹 A에 컨슈머 3명, 파티션 3개 | 한 명당 파티션 1개 |
| 그룹 A + 그룹 B가 같은 토픽 구독 | **둘 다 전체 메시지를 받음** (서로 방해 안 함) |

→ "알림 팀"과 "로그 팀"이 같은 주문을 각자 처리하고 싶을 때 그룹을 나눈다.

## 카프카 vs 일반 큐 vs API 호출

| | 동기 API | RabbitMQ 같은 큐 | 카프카 |
|--|----------|------------------|--------|
| 목적 | 지금 당장 응답 | 작업 전달 | 이벤트 로그/스트림 |
| 보관 | 거의 없음 | 소비하면 보통 삭제 | **오래 보관** 가능 |
| 다시 읽기 | 어려움 | 제한적 | **쉬움** |
| 여러 구독자 | 직접 호출 여러 번 | 가능하지만 패턴 다름 | 토픽 + 그룹으로 자연스러움 |
| 잘 맞는 곳 | CRUD, 조회 | 짧은 작업 큐 | 로그, 이벤트, 대용량 스트림 |

## 메시지 안에는 뭐가 들어가나?

보통 이런 JSON을 넣는다.

```json
{
  "orderId": "ORD-1001",
  "userId": "U-42",
  "amount": 15000,
  "orderedAt": "2026-11-06T14:00:00+09:00"
}
```

포인트:
- **키(key)** 를 넣으면 같은 키는 같은 파티션으로 간다  
  예: `userId`를 키로 → 같은 유저 이벤트는 순서 보장
- 값(value)은 실제 내용
- 헤더에 메타데이터(버전, trace id 등)를 넣을 수도 있다

## 쓰는 흐름 (개념)

### Producer 쪽

1. 카프카 주소(bootstrap servers) 설정
2. 어떤 토픽에 보낼지 정함
3. 메시지(key + value) 전송
4. 성공/실패 확인 (ack)

### Consumer 쪽

1. 같은 카프카 주소 설정
2. 그룹 아이디 정함 (`group.id`)
3. 토픽 구독
4. 폴링(poll)으로 메시지 가져옴
5. 처리 후 오프셋 커밋 ("여기까지 처리함")

## 코드 느낌 (개념용)

언어마다 라이브러리가 다르지만, 흐름은 비슷하다.

### 보내기 (Producer)

```js
// 의사코드 — 실제 라이브러리 API는 환경마다 다름
await producer.send({
  topic: "order-created",
  messages: [
    {
      key: "U-42",
      value: JSON.stringify({ orderId: "ORD-1001", amount: 15000 }),
    },
  ],
});
```

### 받기 (Consumer)

```js
// 의사코드
consumer.subscribe({ topic: "order-created" });

await consumer.run({
  eachMessage: async ({ topic, partition, message }) => {
    const data = JSON.parse(message.value.toString());
    // 재고 차감, 알림 발송 등 비즈니스 처리
    console.log(topic, partition, data);
  },
});
```

## 웹개발자가 자주 헷갈리는 포인트

### 1) "실시간"인가?

카프카는 **거의 실시간에 가깝게** 흐르지만, WebSocket처럼 "브라우저와 바로 연결"하는 기술은 아니다.  
보통 서버 ↔ 서버 이벤트 파이프다.

### 2) 메시지가 정확히 한 번만 처리되나?

기본은 **"최소 한 번(at-least-once)"** 쪽에 가깝다.  
네트워크 문제로 같은 메시지를 두 번 받을 수 있으니,  
**멱등 처리**(같은 주문 두 번 와도 한 번만 반영)를 신경 써야 한다.

### 3) 순서는 항상 보장되나?

**파티션 안에서는** 순서가 보장된다.  
토픽 전체 순서는 파티션을 나누는 순간 깨질 수 있다.  
순서가 중요하면 같은 키로 같은 파티션에 보내라.

### 4) 컨슈머가 죽으면?

같은 그룹의 다른 컨슈머가 파티션을 넘겨받는다(리밸런스).  
오프셋이 있으면 이어서 읽는다.

## 언제 쓰면 좋은가 / 아닌가

**좋은 경우**
- 주문, 결제, 로그처럼 이벤트가 계속 발생
- 여러 팀이 같은 이벤트를 각자 처리
- 장애 후 과거 이벤트를 다시 재생해야 함
- 트래픽이 커서 버퍼가 필요함

**과한 경우**
- 단순한 CRUD API만 있는 작은 서비스
- 브라우저 ↔ 서버 즉시 양방향 통신 (그건 WebSocket)
- 메시지 양이 적고 DB 하나로도 충분한 경우

---

## WebSocket이랑 같이 쓰는 그림

실무에서 자주 이렇게 붙인다.

```
[브라우저] ←WebSocket→ [알림 서버] ←구독─ [카프카] ←발행─ [주문 서버]
```

1. 주문 서버가 `order-created`를 카프카에 넣음
2. 알림 서버가 그걸 소비함
3. 해당 유저 WebSocket으로 "주문 완료" 푸시

역할 분담:
- **카프카**: 서버들 사이의 이벤트 버스
- **WebSocket**: 서버 → 브라우저 실시간 전달

자세한 WebSocket 설명은 [웹소켓.md](./웹소켓.md) 참고.

## 체크리스트 (처음 붙일 때)

- [ ] 토픽 이름 규칙을 정했나? (`도메인-행동`, 예: `order-created`)
- [ ] 파티션 키를 뭘로 할지 정했나? (순서 필요한 기준)
- [ ] Consumer Group 이름을 서비스 단위로 나눴나?
- [ ] 실패 메시지 재처리 / DLQ 정책을 생각했나?
- [ ] 중복 소비에 대비한 멱등 처리가 있나?
- [ ] 로컬/개발용 카프카(또는 관리형 서비스) 접속 정보를 분리했나?

## 더 보면 좋은 키워드

나중에 깊게 볼 때:

- Zookeeper / KRaft (클러스터 메타데이터 관리)
- ISR, replication factor (복제)
- exactly-once / 트랜잭션
- Schema Registry (Avro, JSON Schema)
- Kafka Connect, Kafka Streams

지금 단계에서는 **Producer / Consumer / Topic / Partition / Offset / Group** 만 확실히 알면 충분하다.
