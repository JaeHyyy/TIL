# 웹소켓 (WebSocket)

> 처음 쓰는 사람 기준으로, **용어 → 개념 → 쓰는 법** 순서로 정리한다.

---

## 한 줄 요약

**WebSocket은 브라우저와 서버가 한 번 연결해 두고, 서로 언제든 메시지를 주고받는 통로**다.  
채팅, 실시간 알림, 협업 커서처럼 **"새로고침 없이 바로 반영"** 이 필요할 때 쓴다.

---

## 왜 HTTP만으로는 부족할까?

일반 HTTP 요청은 대략 이런 구조다.

```
브라우저: "데이터 줘"
서버:     "여기 있어"  → 연결 끝
```

서버가 먼저 "너한테 소식 왔어!" 라고 **먼저 말을 걸 수가 없다.**  
(정확히는 폴링, SSE 같은 우회는 있지만, 양방향엔 WebSocket이 직관적이다.)

### 흔한 우회들

| 방식 | 설명 | 한계 |
|------|------|------|
| **폴링** | 클라이언트가 주기적으로 "새 거 있어?" 질문 | 트래픽 낭비, 지연 |
| **롱폴링** | 서버가 답 있을 때까지 연결 유지 | 구현 복잡, 여전히 요청-응답 |
| **SSE** | 서버 → 클라이언트 단방향 스트림 | 브라우저→서버는 따로 HTTP |
| **WebSocket** | 양방향 지속 연결 | 연결 관리, 스케일 설계 필요 |

---

## 핵심 용어

| 용어 | 쉬운 말 |
|------|---------|
| **HTTP** | 요청하면 응답 받고 끝내는 기본 웹 통신 |
| **WebSocket** | 연결을 유지한 채 양방향 메시지 주고받기 |
| **Handshake (핸드셰이크)** | HTTP로 시작해서 WebSocket으로 **업그레이드**하는 과정 |
| **Frame (프레임)** | WebSocket으로 오가는 데이터 조각 |
| **ws:// / wss://** | WebSocket 주소. `wss`는 HTTPS처럼 암호화 |
| **Ping / Pong** | 연결 살아있는지 확인하는 하트비트 |
| **Room / Channel** | (라이브러리 개념) 같은 주제 구독자끼리 묶는 방 |
| **Broadcast** | 연결된 여러 클라이언트에게 한꺼번에 보내기 |

---

## 연결이 생기는 과정

```
1) 브라우저 → 서버 : "WebSocket으로 바꿔줘" (HTTP Upgrade 요청)
2) 서버 → 브라우저 : "OK, 바꿨음" (101 Switching Protocols)
3) 이후부터는 WebSocket 프레임으로 서로 메시지 주고받음
```

한 번 연결되면:

```
브라우저  ←――――――――→  서버
        (계속 열려 있음)
```

- 서버가 먼저 푸시 가능
- 클라이언트가 수시로 전송 가능
- HTTP처럼 매 요청마다 헤더를 왕창 안 실어도 됨

---

## HTTP vs WebSocket

| | HTTP | WebSocket |
|--|------|-----------|
| 연결 | 요청마다 새로 (또는 keep-alive라도 요청-응답 단위) | **한 번 맺고 유지** |
| 방향 | 주로 클라이언트 → 서버 | **양방향** |
| 서버 선제 전송 | 기본 불가 | **가능** |
| 데이터 단위 | Request / Response | Message (텍스트/바이너리) |
| 잘 맞는 곳 | API, 페이지, 파일 | 채팅, 알림, 실시간 현황 |

둘은 대체 관계가 아니다.  
**일반 API는 HTTP, 실시간 채널만 WebSocket** 으로 나누는 게 흔하다.

---

## 어디에 쓰나?

- 채팅 / 고객센터 상담
- 주문 상태, 배송 위치 실시간 갱신
- 알림 벨 (새 메시지 도착)
- 협업 문서, 화이트보드
- 주식/시세, 대시보드 수치
- 게임 매치 상태

**안 써도 되는 경우**
- 폼 저장, 목록 조회 같은 일반 CRUD
- 하루 몇 번뿐인 알림 (이메일/푸시로 충분)
- SEO가 중요한 문서 페이지 본문

## 브라우저에서 쓰는 법 (기본)

순수 WebSocket API:

```js
// wss = 암호화 (HTTPS 사이트면 보통 wss 필수)
const socket = new WebSocket("wss://example.com/ws");

socket.addEventListener("open", () => {
  console.log("연결됨");
  socket.send(JSON.stringify({ type: "join", room: "order-42" }));
});

socket.addEventListener("message", (event) => {
  const data = JSON.parse(event.data);
  console.log("수신:", data);
});

socket.addEventListener("close", () => {
  console.log("연결 종료");
});

socket.addEventListener("error", (err) => {
  console.error("에러:", err);
});
```

서버가 보내는 예:

```json
{ "type": "order-updated", "status": "SHIPPED" }
```

클라이언트가 화면만 바꾸면 된다. 새로고침 없음.

## 서버 쪽 개념

서버는 "연결된 소켓 목록"을 들고 있어야 한다.

```
연결된 클라이언트
┌────────┬────────┬────────┐
│ user-1 │ user-2 │ user-3 │
└────────┴────────┴────────┘
         │
   "user-2에게만 알림"
```

자주 하는 일:
1. 연결 수락
2. 인증 (토큰 확인)
3. 방/유저에 매핑
4. 메시지 수신받기
5. 끊기면 목록에서 제거
6. 재연결 대비

Node 예시 느낌 (의사코드):

```js
wss.on("connection", (socket, request) => {
  const userId = getUserIdFromToken(request);
  sockets.set(userId, socket);

  socket.on("message", (raw) => {
    const msg = JSON.parse(raw.toString());
    // 방 브로드캐스트 등
  });

  socket.on("close", () => {
    sockets.delete(userId);
  });
});
```

실무에선 `ws`, `Socket.IO`, Spring WebSocket, ASP.NET SignalR 같은 걸 많이 쓴다.  
Socket.IO / SignalR은 **재연결, 방, 폴백**을 라이브러리가 도와주는 상위 레이어다.

## 메시지 설계 팁

텍스트로 JSON을 주고받는 게 제일 흔하다.

```json
{
  "type": "chat.message",
  "payload": {
    "roomId": "r-1",
    "text": "안녕하세요",
    "sentAt": "2026-11-06T14:30:00+09:00"
  }
}
```

추천:
- `type`으로 분기하기 쉽게
- 한 메시지 = 한 의도
- 너무 큰 파일은 WebSocket 대신 **업로드 API + URL만 전달**

---

## 끊김과 재연결

모바일/와이파이는 연결이 자주 끊긴다.

꼭 생각해둘 것:
1. **자동 재연결** (지수 백오프: 1초 → 2초 → 4초…)
2. **하트비트(ping/pong)** 로 좀비 연결 정리
3. 재연결 후 **못 받은 메시지 보충** (REST로 최근 내역 조회 등)
4. 서버 배포 시 기존 연결이 끊김 → 클라이언트 재연결이 정상 동작이어야 함

---

## 인증은 어떻게?

WebSocket은 브라우저 `WebSocket` API에서 **커스텀 헤더를 못 넣는 경우**가 많다.

흔한 패턴:
1. 먼저 HTTP로 로그인 → access token 확보
2. 연결 URL 쿼리 또는 첫 메시지로 토큰 전달  
   예: `wss://api.example.com/ws?token=...`
3. 서버가 토큰 검증 후 연결 유지 / 거절

주의: 쿼리 토큰은 로그에 남을 수 있으니, 가능하면  
**짧은 일회용 티켓**을 HTTP로 발급 → WebSocket에 쓰는 방식이 더 안전하다.

## 스케일아웃 문제 (중요)

서버가 1대면 쉽다.  
서버가 2대 이상이면:

```
유저A ──접속──→ 서버1
유저B ──접속──→ 서버2
```

서버1이 유저B에게 직접 메시지를 못 보낸다.  
그래서 **백플레인**이 필요하다.

```
서버1 ──발행──→ (Redis Pub/Sub 또는 카프카) ──구독──→ 서버2 → 유저B
```

정리:
- WebSocket: 브라우저 ↔ 내 서버 인스턴스
- Redis/Kafka: 서버 인스턴스끼리 메시지 공유

카프카와 같이 쓰는 그림은 [카프카.md](./카프카.md) 참고.

---

## 카프카랑 뭐가 다르냐?

| | WebSocket | 카프카 |
|--|-----------|--------|
| 주 사용자 | 브라우저 ↔ 서버 | 서버 ↔ 서버 |
| 보관 | 보통 안 함 (지나가면 끝) | 토픽에 쌓아둠 |
| 목적 | 즉시 UI 반영 | 이벤트 파이프라인 |
| 재처리 | 기본 약함 | 오프셋으로 다시 읽기 가능 |

한 줄:
- **사람에게 바로 보여주려면 WebSocket**
- **시스템끼리 이벤트를 흘리려면 카프카**
